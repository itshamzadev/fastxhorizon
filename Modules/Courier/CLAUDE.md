# Courier Module

Provider-agnostic courier/logistics integration built as an **isolated, portable addon** (`nwidart/laravel-modules`). Core has **zero hard dependency** on this module: enable/disable/remove it without breaking the host app.

One pattern, not four: a **strategy** (swappable provider drivers) resolved and orchestrated by **one service**, persisting through **Eloquent models** directly.

## Golden rules
- Core NEVER `use`s a module class. Integration is via the container (resolve `CourierService`, guarded by `app()->bound()`), config, and events only.
- Drivers and the module NEVER reference a host class (no `App\Models\Order`, no `auth()`, no core settings helper). The module takes normalized DTOs in and emits an event out.
- Every provider operation goes through the `CourierProvider` abstract. Consumers depend on that type + DTOs, never on a concrete vendor driver.

## Owner: the fourth axis
Configuration belongs to an **owner** — the platform (admin) or one vendor — carried as `owner_type` + `owner_id` on `courier_provider_settings`, `courier_shipments` and `courier_provider_addresses`. One table each, no per-panel duplicates.

**Read by filter, never by fallback.** `ProviderRegistry` queries settings with `->forOwner($this->owner())` and nothing else. A vendor with no row for a provider has that provider unconfigured and disabled — the platform's row is not consulted. Do not reintroduce inheritance: it would force three further decisions (whole-set or per-field, does enablement inherit, can a vendor opt out) that nothing asks for.

**Ownership enters through one contract.** `app/Contracts/CourierOwnerResolver.php` → `CourierOwner`. The module ships `PlatformOwnerResolver` via `bindIf`, and the host binds `App\Services\Courier\HostCourierOwnerResolver`. That indirection is what keeps `auth()` out of the module; without a host binding everything is platform-owned, exactly as before the owner axis existed.

**The panel decides the owner, not the guard.** The host resolver reads the current route's name off the request: `vendor.*` acts as the authenticated seller, everything else — admin, storefront, webhook, console — acts as the platform. It must not simply read `auth('seller')`: `admin` and `seller` are sibling session guards over one session cookie and no login path logs the other out, so a browser holding both sessions made *every* admin-panel save write into whichever vendor was signed in. A `vendor.*` route that cannot name its seller **throws** rather than degrading to the platform owner, and rather than casting null to a `vendor:0` row belonging to nobody. The `vendor.` name prefix is therefore load-bearing; `CourierConfigPersistenceTest` walks every registered courier route and asserts the resolved owner matches its panel, so a misnamed vendor route fails CI instead of corrupting data.

The seller app is the one caller with no panel route: `api/v3/seller/*` is unnamed and authenticates by bearer token, so `seller_api_auth` puts the resolved `Seller` model on the request and the host resolver reads it before it looks at the route name. The `instanceof Seller` check is what makes that safe — a request that never passed the middleware can still carry a `seller` input, but it carries a scalar, not a model.

`ProviderRegistry::forOwner()` returns a **scoped clone**, never a mutated singleton — one request legitimately spans owners (an admin opening a vendor's order tracks a shipment booked on the vendor's account), and a mutated singleton would silently reuse the wrong credentials.

**A shipment records the account that booked it.** `ship()` stamps the driver's owner; `resolveForConsignment()` scopes the registry to that stored owner, so track/cancel/update/COD reach the account holding the consignment. `supportsTracking()` takes an optional owner for the same reason. The address book keys on the owner too, because a carrier-issued address id only exists inside the account that created it.

**Webhooks carry their owner in the URL**: `courier/webhook/{provider}/{owner?}`, the segment being `CourierOwner::routeKey()` (`vendor-12`). Verification precedes parsing, so the owner cannot come from the consignment id — each owner registers its own callback URL, surfaced as a copyable field on the config screen. No segment means the platform, which is what every pre-existing registration relies on. The segment is not a security boundary; it only picks which credentials attempt verification.

**Config has a controller per panel; one service and one FormRequest behind all of them.** `Controllers/{Admin,Vendor}/CourierConfigController` each name their own view directly, `Controllers/SellerApi/CourierConfigController` answers JSON, and all three delegate to `app/Services/CourierConfigService.php`, the single place a configuration row is written. Validation is `app/Http/Requests/SaveCourierProviderRequest.php` — deliberately **not** under `Requests/Admin/` or split per panel, because the rules do not differ by owner and each panel's routes already carry the `admin` / `seller` guard middleware that authorizes the request. There is no `panel` route default any more; do not reintroduce one.

`CourierDispatchController` and `CourierLocationController` are still `Admin`-namespaced and shared by both web panels. That is inconsistent with config and worth splitting, but it touches both order-details blades, so it is deliberately a separate change. The seller API reuses `CourierLocationController` verbatim — it is pure JSON with no panel assumption — and has its own `SellerApi/CourierDispatchController` because dispatch must answer JSON where the web action answers `back()` with a toast.

**The seller API is a third panel: `routes/seller_api.php`, `Controllers/SellerApi/*`, deliberately unnamed routes.** Naming them `vendor.*` would send `HostCourierOwnerResolver` down its session-guard branch instead of reading the token's `Seller`; naming them anything else would make `CourierConfigPersistenceTest` demand they resolve the platform owner. `Http/Middleware/ForceJsonResponse` fronts the group so the `vendor_delivery_partner_setup` `404`, validation `422`s and the auth `401` are JSON whatever the client's `Accept` header says. Its `track` action passes `ProviderRegistry::owner()` into `CourierService::track()` / `refreshStatus()`, whose `?CourierOwner $viewer` parameter scopes `resolveForConsignment()` to what that caller may read. An omitted viewer resolves globally on purpose (an admin tracks a vendor's shipment), which is safe on a guarded panel and not on a token-authenticated one. **Scoping must happen inside the resolution, not as a controller pre-check** — `(provider, consignment_id)` is deliberately not unique, so a caller-side `exists()` and the service's own `active()->latest()` lookup could land on different owners' rows, handing one vendor another's tracking events and writing `ShipmentStatusUpdated` against their order. `track()` therefore also refuses an unresolvable consignment outright rather than letting `driver(null)` fall back to the default provider.

**Booking the shipment and being allowed to read it are two different questions.** A vendor whose `vendor_delivery_partner_setup` is off never books anything — the admin books on the platform's account, against the vendor's order — so scoping the seller API by *who booked it* left every one of those consignments answering `No shipment was found for this consignment.` while the vendor panel, which passes no viewer, showed the timeline for the same id. `readableShipment()` therefore tries the viewer's own row first and then falls back to the latest row a second contract permits: `app/Contracts/CourierShipmentAccessResolver.php` → `allowsRead(viewer, bookedBy, hostOrderReference)`. The module ships `BookingOwnerAccessResolver` via `bindIf` (owner match only, i.e. the behaviour before this existed), and the host binds `App\Services\Courier\HostCourierShipmentAccessResolver`, which answers the one question only the host can: is `host_order_reference` an order of that seller's. That keeps `App\Models\Order` out of the module for the same reason `CourierOwnerResolver` keeps `auth()` out of it. The fallback walks candidates (active rows first) and returns the first readable one rather than authorizing a single pre-picked row — a carrier sandbox that hands the same consignment id to several orders would otherwise deny a vendor their own parcel because the newest row belongs to someone else.

The views stay separate — admin is Bootstrap 5 with an offcanvas, vendor is Bootstrap 4 with a modal — so never share markup or classes between `admin/config/*` and `vendor/config/*`. `_field-label.blade.php` is the exception: it already branches on `$courierBs`.

**Credential rules are derived from the driver, never hand-written.** `SaveCourierProviderRequest` resolves the driver, applies the **submitted** country to it, then emits one rule per declared field from `credentialFields()`: `required`/`nullable` exactly as the driver declares, `string`, a length bound, and `Rule::in()` over the option ids of a `select` **for that country** — which is what stops a value chosen for the previous country surviving a country change. Two consequences before you touch a driver: a `required` flag that is not truthfully required now *blocks saves* rather than just painting an asterisk, and a wrong `countryProfiles()` option set now *rejects* a save rather than mislabelling a dropdown. A submission carrying no `credentials` key at all — the card's status toggle — gets none of these rules, because it is not editing the credential set.

**Two known gaps, left open on purpose.** A provider can still be enabled with an incomplete credential set (the UI hides the toggle, so it takes a stale page or a crafted request), and stored credentials — including every `type => 'password'` field — are still rendered into the config forms' `value` attributes, where browser password autofill can overwrite a working secret. Both are pre-existing, neither is what merchants reported, and fixing the second changes the screens. Each deserves its own change rather than being smuggled into this one.

The vendor screen is gated by the host: business setting `vendor_delivery_partner_setup` (default on) → `vendorDeliveryPartnerConfigAvailable()` → the `vendor_delivery_partner_config` middleware alias named on the module's vendor config routes. The module reads no core setting; it only names the alias.

**Setting a partner up and booking one are separate permissions.** Business setting `third_party_delivery_service` is the feature switch for **booking**, not for configuration → `deliveryPartnerServiceAvailable()` → the `delivery_partner_service` alias on the admin dispatch/location routes. Credentials are entered before the service is ever switched on, so the config screens sit behind `delivery_partner_config` / `vendor_delivery_partner_config` instead — `deliveryPartnerConfigAvailable()` asks only whether the addon itself is live, and the vendor variant adds the admin's `vendor_delivery_partner_setup` setting. A merchant can therefore configure and enable a provider with the master switch off; `deliveryPartnerAvailable()` still hides the assignment UI on order details, so nothing can be dispatched until the switch goes on. Both config screens say so in a banner, fed by the host through a `View::composer` in `AppServiceProvider` (`$deliveryPartnerServiceEnabled`) rather than by the module reading a core setting.

**Two gates, one master — for booking.** The vendor booking gate is strictly stronger than the admin's: `vendorDeliveryPartnerSetupAvailable()` calls the master helper first, so the vendor and seller-API booking groups need only the one alias they already name. The seller API's config endpoints deliberately stay on `vendor_delivery_partner_setup`, master switch included: the app decides whether to render its courier screen at launch from `vendor_delivery_partner_setup_status` in `GET /api/v1/config`, so loosening the route without a matching flag would leave the endpoint reachable and the screen still hidden. `track` sits outside every gate on every panel: the order-details card still renders an existing shipment when the switch is off, and its Track button must keep working. Webhooks are ungated for the same reason — a carrier's status callback for an already-booked parcel must land whatever the admin has switched off. All four middlewares refuse the same way (`DeliveryPartnerServiceMiddleware`, which `VendorDeliveryPartnerSetupMiddleware` and `DeliveryPartnerConfigMiddleware` extend, the latter extended in turn by `VendorDeliveryPartnerConfigMiddleware`): `404` when the request expects JSON, so the seller app's documented "hide the courier screen on 404" contract holds and panel AJAX still reads the gate from the status code; a toast plus a redirect back for a browser navigation, because a merchant who reaches a disabled screen by URL needs an explanation, not a dead end. The redirect picks its fallback from the **route name** (`vendor.*`), never the guard — admin and seller are sibling session guards over one cookie.

## Shape

Host app (6Valley / 6amMart)
  │  ships a normalized OrderData ───────────────────────────►  ┐
  │  listens to ShipmentStatusUpdated ◄───────────────────────  │   (two loose touchpoints)
  ▼                                                              ▼
CourierService (orchestration) ── uses ──► ProviderRegistry (resolution)

   • handleWebhook(provider, request)          • isProviderEnabled / catalog
   • track/cancel/updateShipment/codCollection • injects creds

                                                        ▼

                                          └─ PathaoProvider, RedxProvider, …

## Request lifecycle (Send to courier) — end to end
The full path from a click to the Pathao API, top to bottom:
1. `CourierDispatchController::store(SendToCourierRequest)` — the FormRequest already validated input (and confirmed the chosen provider is enabled) and exposes `toOrderData()` + `selectedProvider()`. The controller only delegates.
2. `CourierService::ship(OrderData $order, string $provider)` — enforces the invariants (provider enabled, order not already shipped), then asks `ProviderRegistry::driver($provider)` to **resolve the driver** (`container->make(registry[$provider])` → `setCredentials(...)`), and checks `$driver instanceof CreatesOrders`.
3. `PathaoProvider::createOrder(OrderData)` — maps the DTO to Pathao's payload and makes **the actual external HTTP call**: `$this->http()->post('/aladdin/api/v1/orders', ...)`. This one line is where the request leaves the app.
4. Back in `ship()`: persist a `CourierShipment` row and return a `ShipmentResult`.

`ProviderRegistry` is a **collaborator, not a call-path layer** — controllers still talk only to `CourierService` (or, for pure resolution concerns like the admin config/location screens, to `ProviderRegistry` directly). The dispatch path stays controller → service → provider.

## Why a registry + `driver($name)` (not container interface binding)
Because a provider is chosen **per order at runtime** (multiple can be enabled at once), there is no single "active" implementation to bind `CourierProvider::class` to. A container binding resolves one type to one implementation per context; it cannot express "the provider named in *this* request" or "the provider that created *this* shipment". So resolution is a factory keyed by id — `ProviderRegistry::driver($name)`. The registry (`config('courier.providers')`) is also what lets the admin UI **enumerate every** provider (enable toggles, credential forms) and what makes adding a provider one config line with no container wiring.

## Where each check lives (no duplication)
- **Is the provider enabled?** — one method, `ProviderRegistry::isProviderEnabled()`. Called by `SendToCourierRequest` (to show the admin a friendly validation error) and re-asserted in `CourierService::ship()` (the domain invariant, for any host that calls `ship()` directly without the FormRequest). Same rule, one source of truth, two layers of defense.
- **Does the driver support this operation?** — `$driver instanceof <Role>` where `CourierService` consumes it. Capability is expressed by type, a **different** question from enablement.
- **Already shipped?** — the dedup invariant lives only in `ship()`.

## Key files
- Base: `CourierProviders/CourierProvider.php` — abstract identity + shared `http()`/`failFromResponse()`; no operations.
- Role interfaces: `CourierProviders/Contracts/*` — one per operation; drivers implement only what they support (ISP).
- Drivers: `CourierProviders/<Name>Provider.php` extend `CourierProvider` and implement role interfaces.
- Service: `app/Services/CourierService.php` — host-facing orchestration only. Host entry points: `ship`, `handleWebhook`, and post-dispatch ops `track` / `cancel` / `updateShipment` / `codCollection` (each resolves the shipment's own provider; optional per provider). The host resolves this (guarded by `app()->bound()`).
- Registry: `app/Services/ProviderRegistry.php` — provider resolution: `driver()`, `enabled()`, `isProviderEnabled()`, `catalog()`, credential injection. Used by `CourierService` and by the config/location screens directly.
- Config save: `app/Services/CourierConfigService.php` — the one write path for `courier_provider_settings`, used by both panels' config controllers and by tests (no HTTP action needed, which matters because the controllers' toast pulls in the host's `business_settings` table).
- Enums: `app/Enums/ShipmentStatus.php` (common status vocabulary).
- DTOs: `app/DataTransferObjects/{Requests,Responses}` — normalized payloads; added per-operation as built.
- Event: `app/Events/ShipmentStatusUpdated.php` — the module → host channel.
- Models (used directly, with scopes): `app/Models/*`. `courier_shipments.host_order_reference` links to the host order BY VALUE (no FK) so the module stays removable.
- Address book: `app/Models/CourierProviderAddress.php` + `courier_provider_addresses`. Only for carriers that require an address record to exist before an order can reference it (Garuda Express; Delhivery shares the pattern). Maps a hashed normalized address → the carrier's address id, scoped by owner, provider **and** environment, so a repeat order reuses the record instead of creating a duplicate, a sandbox id can never reach a live payload, and one merchant's address id never appears in another's request. Drivers that send recipient details inline never touch it.
- Owner: `app/ValueObjects/CourierOwner.php`, `app/Contracts/CourierOwnerResolver.php`, `app/Services/PlatformOwnerResolver.php` — see "Owner: the fourth axis" above.
- Webhooks: `routes/webhook.php` → `Http/Controllers/Webhook/CourierWebhookController.php`.
- Seller app API: `routes/seller_api.php` → `Http/Controllers/SellerApi/*`, documented endpoint by endpoint in `docs/courier-app-api.md`.

## Provider contract (role interfaces — ISP)
`CourierProvider` (abstract) carries only cross-cutting identity + shared HTTP infra: `getName()`, `getLabel()`, `credentialFields()`, `setCredentials()`, `http()`, `failFromResponse()`, `webhookAcknowledgement()`. It declares **no operations**.

**Labels are composed, not written out.** A driver overrides `displayName()` (the brand) and declares `supportedCountries()` (ISO-3166 alpha-2 codes); the base derives `coverage()` from them and `getLabel()` renders `"<displayName> (<coverage>)"` — e.g. `Pathao (Bangladesh)`, `Pathao (Nepal)`, `Lalamove (Multinational)`, and `Lalamove (Bangladesh)` once a market is selected. Do **not** override `getLabel()` or `coverage()`, and do not bake the brackets into a name string: the format lives in one place, and same-brand markets stay distinguishable in the admin config cards and the order-details delivery-partner list, which are the only consumers (via `ProviderRegistry`). Every registered driver must declare a non-empty `supportedCountries()` of valid ISO codes — a contract test enforces it.

**The operating country is a third axis of driver state, alongside credentials and environment.** `supportedCountries()` declares what a carrier serves; `setCountry()` / `country()` carry the merchant's selection, with the same "ignore anything unsupported" guard as `setEnvironment()`. `country()` falls back to the first supported code, so a single-country driver is correct with one declaration and no admin input. `ProviderRegistry::make()` injects it from `courier_provider_settings.settings['country']` — the same JSON column that holds `environment`, so there is no extra table and no migration.

A **multinational** driver (`DhlProvider`, `LalamoveProvider`, `AramexProvider`) additionally declares `countryProfiles()`: a `code => [...]` map holding the per-market values its requests depend on — Lalamove's `Market` header, language keys, vehicle catalogue and calling code; DHL's currency and domestic/international product codes; Aramex's currency and station entities. `supportedCountries()` is derived from that map's keys (DHL excepted — it serves every country and its map is an override table over `DEFAULT_PROFILE`), so the two can never drift. Country-dependent credential fields are rendered as `type => 'select'` scoped to the active profile rather than as free text, and the market-identifying credentials they replaced (`market`, `origin_country_code`, `account_country_code`) are gone. `legacyCountryCredential()` names the removed key so `ProviderRegistry` can seed the country from an upgraded install's existing credentials.

Each operation is a small role interface in `CourierProviders/Contracts/`: `CreatesOrders`, `UpdatesOrders`, `CancelsOrders`, `ProvidesOrderInfo`, `TracksOrders`, `ResolvesLocations`, `CalculatesPrice`, `EstimatesDeliveryCharge`, `CollectsCod`, `HandlesWebhooks`. A driver `implements` only the roles it truly supports — so capability is expressed by **type**, and there is no fat base, no refused-bequest throwing (LSP), no `$capabilities`/`supports()`/`guard()`/`CourierOperation` apparatus.

## Add a new provider (plug-and-play)
1. Create `CourierProviders/<Name>Provider.php` extending `CourierProvider`, `implements` the role interfaces it supports.
2. Implement those interface methods (each is required by the interface — no guard boilerplate).
3. Override `displayName()` and declare `supportedCountries()` so the driver labels itself (see Provider contract above). A carrier serving several markets also declares `countryProfiles()` and `legacyCountryCredential()`.
4. Add one line to `config/config.php` `providers`: `'<id>' => <Name>Provider::class`. `getName()` must return `<id>`.
5. Done — no core changes.

## A tracking event may carry no status
RedX's `/parcel/track` returns `message_en` + `time` and no status field at all. `RedxProvider::mapTrackingMessage()` resolves the message strings **confirmed against RedX** to the shared vocabulary and leaves everything else `ShipmentStatus::Unknown`; `app/Http/Concerns/PresentsTrackingEvents.php` is the one place both dispatch controllers turn `TrackingEvent`s into JSON, and it labels an unmapped event with the carrier's message rather than the word "unknown".

**A timeline row and the status field must speak one language.** An unmapped row is headed by the carrier's sentence, so "Package is created successfully" sat directly under a `Shipment Status: Pending` — two vocabularies describing one moment, which reads as a contradiction even though both are right. A mapped event is headed by its status (`Pending`) with the carrier's sentence kept underneath as the description, so the two agree and nothing the carrier said is lost. Extend the map **only** with messages seen in a real RedX response — inventing the rest is the guesswork that keeps the Leopards/Domex drivers parked, and a wrong mapping now misstates a status instead of merely mislabelling a row.

**The status badge follows the shipment, never an event.** A tracking event is a carrier message log; the shipment's `status` column is the fact. So the track endpoint answers with a `status` block alongside `events`, `syncBadge()` reads only that, and no consumer may derive a status from `events[0]` — doing so is what first painted a correctly stored `pending` as `Unknown`, and then, once unknown events were ignored, left a `Pending` badge sitting beside a "Package is created successfully" event.

That badge would otherwise be frozen at whatever `ship()` recorded, because only a webhook ever moved it and four of the ten drivers have none (and a sandbox fires none at all). `CourierService::refreshStatus()` closes that gap: on the merchant opening the timeline it calls the driver's `ProvidesOrderInfo::getOrderStatus()` — RedX's `/parcel/info`, which *does* carry a mappable status — persists any change and dispatches `ShipmentStatusUpdated` so the host order follows, exactly as a webhook would. It is deliberately **on demand, not on page load**: an order-details render must not block on a carrier HTTP call. Three cases leave the stored status standing rather than degrade it — a driver with no status lookup, a carrier failure (`rescue`, because a convenience read must not fail the timeline), and a raw status the driver maps to `Unknown`.

**RedX's sandbox exercises none of that.** `sandbox.redx.com.bd/v1.0.0-beta/parcel/info/{id}` answers `503 {"message":"Service is currently unreachable"}` for a consignment its own `/parcel/track` serves `200` for, so on sandbox credentials the refresh always takes the failure branch and the badge legitimately never moves. Verify the status path against live credentials; do not read a motionless sandbox badge as a bug in the refresh.

**Wording is `ShipmentStatus::label()`, and nothing else.** Every screen used to build its own display string with `translate(str_replace('_', ' ', $status))` — the admin/vendor card, both storefront tracking blades, the presenter — so the same status could read four ways. `partial_delivered` labels as **Partially Delivered** and `unknown` as **Not Reported Yet**; the rest are title-cased from the value, `pending` included. The label ships in every payload (`status_label`, `shipment_status_label`, `status.label`) so no consumer — web, app, or API — has to derive it. The stored/serialized **value** never changes; only the wording does.

**A carrier event may predate the dispatch.** RedX's sandbox returns the same canned record for every consignment (`2020-03-16T05:44:24.000Z`, fixed in `TrackingEventPresentationTest`), so a parcel booked today shows a 2020 event beside a today `Dispatched On`. That is the sandbox's data, not a formatting fault: the event time is the carrier's, the dispatch time is ours, and the two are never reconciled.

`TrackingEvent::occurredAt` stays exactly as the carrier sent it — RedX's UTC ISO-8601, Delhivery's offset-bearing scan time, TCS's written-out date — because the DTO is the carrier's answer, not a screen. The presenter is where that becomes readable: it parses the string, converts to `date_default_timezone_get()` (an offset-less carrier string is already local, so the conversion is a no-op) and renders `d M Y, h:i A`, the format `CourierService` already stamps on `dispatched_at`. **Read the timezone from PHP's default, never from `config('app.timezone')`** — the host's admin panel keeps its timezone in a business setting and applies it at boot with `date_default_timezone_set()`, leaving `config('app.timezone')` on the hardcoded file value, so a merchant who changes the setting would see stale times. Going through PHP's default is also what keeps the module off the host's settings helper. A string no parser accepts falls through untouched rather than being dropped, so a driver returning an exotic shape degrades to the raw value instead of an empty cell. Never format in a driver, and never re-expose the raw timestamp on the web timeline or the seller API.

Only one RedX message is mapped today — `package is created successfully` → `pending`, the status `createOrder()` already stamps — because it is the only one the sandbox has ever returned. The rest of RedX's message vocabulary is still needed in writing.

## Carrier store lists are merchant-authored, not catalogue data
Cities, zones and areas come from a carrier's own catalogue; **stores do not** — a merchant types them into the carrier's panel, and a shared sandbox account accumulates whatever every other integrator typed. Pathao's sandbox returns stores named `{{7*7}}`, `{{config}}`, `test$(id)` and ``test`id`` — injection probes left by other developers, indistinguishable from real pickup points to Pathao. `CourierProvider::storeLocations()` is the one place a store row becomes a `Location`, and it drops names carrying template or shell syntax before composing the label. Both `ProvidesStores` drivers go through it; a new one must too, rather than mapping rows itself.

Free text also arrives with newlines and doubled spaces, so `Location` normalizes every name in its constructor — the single chokepoint every driver's options pass through. It strips `\p{Cc}` only: `\p{Cf}` carries ZWNJ/ZWJ, which are meaningful in Bengali, Hindi and Arabic names.

## Partial support
Capability = type. Callers branch on `$driver instanceof <Role>` (see `CourierService::track/cancel/...` and `CourierLocationController`). A provider that lacks a role never advertises it; calling an unsupported op through `CourierService` throws `UnsupportedCourierOperationException` — never an ambiguous vendor error. To add a brand-new operation: add a role interface (+ its return DTO) and `instanceof`-guard it where the service consumes it.

## Conventions (MANDATORY — do not violate)

**No comments.** Write self-documenting code via clear naming and structure — not comment blocks. Do NOT add explanatory comments, section-header comments, step-by-step narration, docblocks that restate the signature, or "// this does X" lines. Only exception: a single comment that captures genuine *why* context (a non-obvious business rule or a spec/vendor quirk) that the code itself cannot express. If the code needs a comment to be understood, rename/refactor instead. This applies to `.php`, `.blade.php`, and every file in this module.

**Validation lives in FormRequest classes, never in controllers.** Controllers must NOT call `$request->validate([...])`, `Validator::make(...)`, or inline validation arrays. Create a dedicated `FormRequest` in `app/Http/Requests/` (e.g. `app/Http/Requests/Admin/SendToCourierRequest.php`) with `rules()` (and `authorize()` / custom `messages()` as needed), then type-hint it in the controller action. Controllers stay thin: they receive an already-validated request and delegate to `CourierService`. One Request class per action that takes input.

## Host integration (per project)
```php
// host → module: map the host order to OrderData inline, then:
$courier = app()->bound(CourierService::class) ? app(CourierService::class) : null;
$courier?->isEnabled() && $courier->ship($orderData);

// module → host: react to status changes without any coupling
Event::listen(ShipmentStatusUpdated::class, fn ($e) => /* update host order by $e->hostOrderReference */);
```
No adapter to implement, no manager, no repository. Debugging a shipment = `CourierService::ship()` → `CourierProvider::createOrder()` → HTTP.

## Status
Foundation complete and exercised. `PathaoProvider` is implemented and verified against the live sandbox (auth+token cache, createOrder, order-info status, city/zone/area, price-plan, webhook verify/parse). Contract is first-class for tracking history, cancel/update, and COD-query (optional per provider).

Ten drivers are registered: `pathao`, `pathao_nepal`, `redx`, `dhl`, `lalamove`, `delhivery`, `aramex`, `shiprocket`, `tcs`, `garuda_express`. `TcsProvider` and `GarudaExpressProvider` are the only ones besides Pathao built from a **first-party specification** (`docs/tcs-courier.md`, `docs/garuda-express-api.md`) rather than reconstructed from third-party wrappers. TCS maps its Country→City→Area→Block hierarchy onto the catalog cascade (city→`city`, area→`zone`, block→`area`), supports both TCS auth flows, and carries the sandbox-simulation credential the Leopards/Domex drivers established.

**Parked drivers.** `LeopardsProvider`, `DomexProvider` and `NepalCanMoveProvider` are commented out of `config/config.php` and therefore invisible to the admin screen and the dispatch form. None of the three carriers publishes an API specification, so those drivers were reconstructed from third-party wrappers and their endpoints, auth schemes and response shapes are unverified — shipping them as selectable options would present guesswork as a working integration. The classes, their mapping logic and their tests are all retained: re-enabling one means uncommenting its registry line and its import once the carrier's own documentation is in hand. Do not delete them, and keep them compiling when the base contract changes.

`PathaoNepalProvider` **extends** `PathaoProvider` and overrides market values only — `getName`/`getLabel`, `baseUrls()`, `currency()`, `deliveryTypes()`. Pathao runs the same Hermes/Aladdin surface per market, so there is exactly one copy of the order mapping, catalog cascade, token exchange and status map. When adding another Pathao market, override values — never behaviour. Its Nepal hosts are **unverified**; the `sandbox_base_url` / `live_base_url` credentials let an admin correct them without a release.

`GarudaExpressProvider` is the module's first **address-book** driver: a TGE order carries no recipient fields, only two address ids, so `createOrder()` resolves delivery then pickup through `CourierProviderAddress` before booking — and persists each mapping *before* the order call, so a failure in between is retry-safe instead of duplicating. Three other TGE quirks are load-bearing: districts are the only geography (`locationLevels()` → `['city']`, relabelled via `locationLabels()`) and must be keyed on `id` because `MNG` is both Morang and Manang; a **wrong** API key returns HTTP 500 (a *missing* one returns 401), so the driver classifies 500-with-an-RFC-2616-body as an auth failure and forces retries off; and TGE publishes **no sandbox host**, so its `sandbox` environment is unconditionally simulated and never reaches the network.

Credential fields support `type => 'select'` (with `options` as `id`/`label` pairs), rendered by `admin/config/_setup-offcanvas.blade.php`. Use it for genuine choices — Garuda's `amount_semantics`, a yes/no toggle, or any field whose valid values follow the selected country — rather than the "enter 1 to enable" text convention. Option labels go through `translate()` by default; set `'translatable_options' => false` on selects whose options are data, not vocabulary (Garuda's 77 districts, Aramex's station codes, Lalamove's language keys) so they never reach the language file.

**The credential form is merchant-facing, not developer-facing.** A field earns its place only if the merchant must supply it: credentials, carrier-issued identifiers, and the pickup identity/address printed on the label. Anything with a universally correct value is a constant in the driver, not a form field — units of measurement, API versions, ClientInfo source codes, planned-ship offsets. Labels use the merchant's words ("Pickup Contact Phone", not "Shipper Phone"; "Pickup Map Latitude" with a Google Maps instruction, not "Latitude"), and `required` is set truthfully because the blade renders the red asterisk from it, `is_configured` is computed from it, **and the save endpoint validates against it** — an untruthful flag blocks saves.

**`deliveryTypes()` is the per-order half of the configuration.** A credential picks the *default* service; `deliveryTypes()` is what lets the admin/vendor override it on a single order, and it is country-scoped where the carrier's catalogue is: Lalamove returns the selected market's vehicles (Hong Kong offers `WALKER` and two truck sizes, Bangladesh does not), Aramex its product types, TCS its service codes, Pathao its two delivery speeds. `ProviderRegistry::enabledOptions()` carries it to `_delivery-partner-fields.blade.php`, which renders the picker only when the chosen provider advertises one. Delivery-type ids are **provider vocabulary, not integers** (`48`, `MOTORCYCLE`, `PPX`, `O`) — the FormRequests validate them as strings and each driver coerces its own type, so never reintroduce an `integer` rule.

**`credentialsComplete()`** expresses configuration rules the per-field `required` flags cannot. Only TCS overrides it: its manual states that not every account has both credential pairs, so either `client_id`+`client_secret` or `username`+`password` satisfies it. Without the hook TCS reported itself Configured with no authentication at all.

**Country profile tables are unverified.** Lalamove's twelve markets (service types, language keys) were reconstructed from the driver's own former `CALLING_CODES` constant, and Aramex's station codes from three examples in its old credential help text. Both are marked in-file. Confirm them against Lalamove's Partner API market reference and the merchant's Aramex contract before go-live; a wrong station is an error on `CreateShipments`, not a silent default. DHL's table is only a currency override map — an absent country degrades to `DEFAULT_PROFILE` (`USD`, `N`, `P`), which is exactly the behaviour the driver had before country selection existed, so an incomplete map is safe. Aramex still implements no `EstimatesDeliveryCharge` role: country selection fixes its currency, station and origin on booking, but a real rate estimate needs its Rate Calculator spec.

**`legacyCountryCredential()` is a compatibility shim with a removal point.** It exists so an install configured before country selection keeps quoting against the market it was set up for. Delete it — and the `countryFor()` fallback branch in `ProviderRegistry` — one release after merchants have had the chance to save a country explicitly.
